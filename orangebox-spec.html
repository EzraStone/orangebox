orangebox is a zero-config local proxy that records every LLM API call your agent makes — prompts, tool calls, streams, retries, tokens, latency, cost — into SQLite, and renders each run as a visual timeline in a local web UI. Point your SDK's base URL at it and press play. Aircraft "black boxes" are actually painted international orange so they can be found. Same idea: when your agent crashes, the evidence survives — hence the name, hence this paint job.

To the implementing AI — read first

This document is the complete build context for orangebox v1. Treat MUST as a hard requirement, SHOULD as a strong default you may deviate from only with a stated reason in code comments, and MAY as optional. Where this spec is silent, choose the simplest option consistent with §02 non-goals. Do not add features not listed here — v1 wins by being small, fast, and finished. Cross-references use section numbers (e.g. "see §07"). All naming, schemas, and endpoint shapes in this document are normative.

§01 · Overview

What orangebox is

One-liner: a local flight recorder for AI agents — run npx orangebox, point your SDK at it, and watch every prompt, tool call, and token stream through a visual timeline you can inspect forever.

The problem. People building agents debug them by reading raw JSON logs and console prints. When an agent loops, stalls, burns tokens, or picks the wrong tool, reconstructing what actually happened — which prompts went out, in what order, with what tool results injected — is manual archaeology. Hosted observability platforms solve this but require accounts, SDK instrumentation, and shipping your prompts to someone's cloud.

The wedge. orangebox requires zero code changes (only an environment variable), stores everything locally, needs no account, and works with any language or framework because it sits at the HTTP layer. It is to agents what Wireshark is to networks: a passive, trustworthy tap.

How it works in one paragraph. orangebox starts an HTTP server on 127.0.0.1:4100. That server does three jobs at once: (1) reverse-proxies API requests to Anthropic and OpenAI, transparently streaming responses back while teeing a copy; (2) parses each captured request/response pair into a normalized "call" record and appends it to a local SQLite database, grouped into "runs"; (3) serves a static single-page UI plus a small JSON API and a live SSE feed so the timeline updates in real time while your agent executes.

§02 · Scope

Goals and non-goals

2.1v1 goals (MUST ship)

  • Transparent pass-through proxy for Anthropic Messages API and OpenAI Chat Completions API, including SSE streaming, with recording that never alters the response the client sees.
  • Automatic grouping of calls into runs, with an explicit opt-in mechanism for precise grouping (§06.4).
  • SQLite persistence with full raw payloads (redacted per §12) plus extracted columns for fast querying.
  • Web UI: run list → run timeline → call detail, updating live during execution (§11).
  • Token counts, latency, TTFT, stop reason, and estimated USD cost per call and per run (§08).
  • Install-to-first-recorded-call in under 2 minutes with exactly two shell commands.
  • Single runtime dependency (better-sqlite3). Everything else: Node standard library.

2.2Non-goals for v1 (MUST NOT build)

  • No accounts, auth, cloud sync, telemetry, analytics, or update pings. Ever, in any version.
  • No replay/re-execution of calls (v2, §19). No diffing between runs (v2).
  • No support for other providers/endpoints (embeddings, images, batch, Gemini, Bedrock) — the architecture must not preclude them, but no code for them ships in v1.
  • No framework-specific adapters (LangChain, Vercel AI SDK, etc.). The HTTP layer is the integration.
  • No config files. All behavior via CLI flags and environment variables.
  • No TypeScript build step, no bundler for the server, no UI framework. Plain ESM JavaScript everywhere.
Decision — why HTTP proxy, not SDK wrapper

An SDK wrapper only works for one language and requires code changes; a proxy works for Python, JS, Go, curl, and every framework simultaneously, and is impossible to forget to instrument. The cost is that we must faithfully handle streaming and edge cases at the HTTP layer (§06, §14). That cost is the product.

§03 · Audience

Users and core stories

Primary persona: a developer building an agent (side project or at work), currently debugging via console.log. Secondary: a developer evaluating token spend. All stories below MUST be demonstrable in the finished v1.

  1. "Why did my agent do that?" — Start orangebox, re-run the agent, open the timeline, click the bad call, read the exact system prompt + message history + tool results the model saw at that moment.
  2. "Where did my agent stall?" — The timeline's proportional spacing and latency chips make the 40-second tool gap or the 3× retry visually obvious without reading anything.
  3. "What is this costing me?" — Each run header shows total tokens and estimated USD; each call shows its share.
  4. "Show a teammate." — orangebox export <run-id> writes a self-contained JSON file of the run (§05.2) that can be committed to a bug report.
  5. "Watch it live." — With the UI open, calls appear within 250 ms of completion; a streaming call shows a live dashed node with elapsed time ticking (§11.4).

§06 · Proxy

Proxy engine

6.1Request handling (MUST)

  1. Match path prefix per §04; extract optional runId; compute upstream URL = provider origin + remaining path + original query string.
  2. Buffer the request body fully (bodies are JSON; cap 10 MB — over cap, forward anyway but store a truncation stub, §14). Record started_at (epoch ms) immediately before dispatching upstream.
  3. Forward using fetch (Node ≥18 / undici) with the original method and body, and headers filtered as follows:
    • Drop hop-by-hop headers: host, connection, keep-alive, transfer-encoding, upgrade, proxy-*, content-length (recomputed).
    • Force accept-encoding: identity upstream so captured bytes are plaintext (pass-through of compressed streams plus capture is not worth the complexity in v1).
    • Pass auth headers (authorization, x-api-key) through to upstream but NEVER persist them (§12.2).
  4. Relay the upstream status code and response headers to the client (minus hop-by-hop and content-encoding/content-length when re-chunking).

6.2Non-streaming responses

Read the full upstream body, send it to the client unchanged, then hand {requestBody, responseBody, status, timing} to the parser (§07). DB writes happen after the client response is finished — never in the hot path.

6.3Streaming responses (SSE)

Detected via request body "stream": true or response content-type: text/event-stream. Requirements:

  • Write-through: every chunk from upstream is written to the client the moment it arrives; capture appends to an in-memory buffer in parallel. No batching, no transformation, no added latency beyond function-call overhead (§13).
  • Record first_token_at on the first SSE event that carries content (Anthropic: first content_block_delta; OpenAI: first chunk with a non-empty choices[0].delta). Record ended_at when the upstream stream closes.
  • After close, reassemble the buffered events into a canonical final response object (§07.3) and persist.
  • If the client disconnects mid-stream: abort upstream, finalize the record with error_type = 'client_aborted' and whatever was captured. If the upstream errors mid-stream: relay what arrived, finalize with error_type = 'upstream_stream_error'.

6.4Run attribution — the grouping rules

Every call gets exactly one run_id, resolved in priority order:

  1. Path-scoped (explicit): requests via /r/:runId/… attach to that run. Created by orangebox run (§05.2) or manually via §10.4. Run rows created this way get source='explicit'.
  2. Header: if the request carries x-orangebox-run-id: <id> (users can set default headers in both SDKs), use it, creating the run row if new.
  3. Gap heuristic (implicit): otherwise, attach to the most recent implicit run if its last call ended less than --gap seconds ago; else create a new run with source='gap' and an auto-name like run 2026-07-27 14:03. This is deliberately simple; concurrent unrelated agents interleaving into one implicit run is accepted v1 behavior — the fix is the explicit mechanisms above, and the UI copy says so.

A run's ended_at is set by the explicit end endpoint, or lazily for implicit runs when a newer run is created.

§07 · Normalization

Parsing & normalization

Two provider modules, src/parse/anthropic.mjs and src/parse/openai.mjs, each export the same interface: parseRequest(json), reassembleStream(sseText), parseResponse(json), returning pieces of the normalized call record below. All parsing MUST be defensive: any unrecognized shape degrades to storing raw JSON with extracted fields null — never a crash, never a dropped record (§14).

7.1Normalized call record (the contract between §06, §09, §11)

7.2Anthropic Messages API mapping

Request (POST /v1/messages): read model, stream, system, messages[], tools[]. Response: content[] blocks of type text and tool_use {id, name, input}; stop_reason ∈ end_turn | tool_use | max_tokens | stop_sequence (store others verbatim); usage {input_tokens, output_tokens, cache_creation_input_tokens → cache_write_tokens, cache_read_input_tokens → cache_read_tokens}.

7.2.1 Stream reassembly algorithm (Anthropic)

  1. Split buffer on SSE framing (event:/data: lines, blank-line delimited); ignore ping.
  2. message_start → seed message object (id, model, role, initial usage).
  3. content_block_start at index i → open block i (text block with text:'', or tool_use with partial_json:'').
  4. content_block_delta → append text_delta.text to text blocks; append input_json_delta.partial_json to tool_use blocks.
  5. content_block_stop → for tool_use, JSON.parse the accumulated string into input (on parse failure keep raw string under input_raw and continue).
  6. message_delta → merge stop_reason and usage.output_tokens. message_stop → done. error event → finalize with error_type='upstream_stream_error' and store the error payload.

7.3OpenAI Chat Completions mapping

Request (POST /v1/chat/completions): read model, stream, messages[], tools[]. Response: choices[0].message with content and tool_calls[{id, function:{name, arguments}}] (arguments is a JSON string — parse for display, keep raw); finish_reason → stop_reason; usage {prompt_tokens → input_tokens, completion_tokens → output_tokens}.

Stream reassembly: concatenate choices[0].delta.content strings; accumulate delta.tool_calls by their index, concatenating function.arguments fragments; take finish_reason from the final carrying chunk; usage arrives only in the terminal chunk when the client sent stream_options.include_usage — when absent, token fields stay null and the UI shows an em-dash with the tooltip "enable stream_options.include_usage for streamed token counts". Terminate on data: [DONE].

7.4Tool event extraction

After persisting a call, extract tool events into their own table (§09) for the timeline's blue track:

  • From the response: every tool_use block (Anthropic) / tool_calls entry (OpenAI) → row with kind='tool_use', tool name, id, JSON input.
  • From the next request's messages: every tool_result block (Anthropic) / role:'tool' message (OpenAI) → row with kind='tool_result', matched to its originating tool_use_id/tool_call_id, with is_error from Anthropic's is_error flag. The wall-clock gap between a call's ended_at and the next call's started_at is rendered as tool-execution time in §11 — orangebox never sees the tool run itself, only its result, and the UI labels it "client-side ≈".
§08 · Accounting

Tokens & cost

Cost per call (USD):

cost = input_tokens/1e6 * in + output_tokens/1e6 * out
     + cache_read_tokens/1e6 * cache_read + cache_write_tokens/1e6 * cache_write

Rates come from src/pricing.json, matched by longest key that is a prefix of the model string (so claude-sonnet-4-6 matches key claude-sonnet-4-6 before claude-sonnet). No match → cost_usd = null; the UI shows "—" with tooltip "no pricing entry for <model>". Null token fields count as 0 in the formula only if at least one token field is non-null; otherwise cost is null.

src/pricing.json — shape (rates are USD per million tokens)
{
  "_comment": "Verify every rate against provider pricing pages at build time; prices drift.",
  "_updated": "YYYY-MM-DD",
  "claude-sonnet-4-6":   { "in": 3.00,  "out": 15.00, "cache_read": 0.30, "cache_write": 3.75 },
  "claude-haiku-4-5":    { "in": 1.00,  "out": 5.00,  "cache_read": 0.10, "cache_write": 1.25 },
  "gpt-4o":              { "in": 2.50,  "out": 10.00 },
  "gpt-4o-mini":         { "in": 0.15,  "out": 0.60 }
}
Implementing AI — do not trust these numbers

The rates above are placeholders demonstrating shape. Before release, populate the file from the providers' current pricing pages and set _updated. If ~/.orangebox/pricing.json exists at boot, deep-merge it over the shipped file so users can correct drift without upgrading. Every cost in the UI is labeled "est." — it is an estimate, not a bill.

§09 · Storage

SQLite layer

better-sqlite3 (synchronous, prebuilt binaries — the project's single dependency). Open with journal_mode=WAL, synchronous=NORMAL, busy_timeout=5000. All writes for one call (call row + tool events + run aggregate update) happen in one transaction, after the client response completes. Schema version stored in meta; v1 migration policy: create-if-missing only.

schema.sql — normative DDL
CREATE TABLE IF NOT EXISTS meta (key TEXT PRIMARY KEY, value TEXT);

CREATE TABLE IF NOT EXISTS runs (
  id            TEXT PRIMARY KEY,
  name          TEXT,
  source        TEXT NOT NULL CHECK (source IN ('explicit','header','gap')),
  started_at    INTEGER NOT NULL,
  ended_at      INTEGER,
  call_count    INTEGER NOT NULL DEFAULT 0,
  input_tokens  INTEGER NOT NULL DEFAULT 0,
  output_tokens INTEGER NOT NULL DEFAULT 0,
  cost_usd      REAL    NOT NULL DEFAULT 0,
  error_count   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE IF NOT EXISTS calls (
  id               TEXT PRIMARY KEY,
  run_id           TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  seq              INTEGER NOT NULL,          -- 1-based order within run
  provider         TEXT NOT NULL,
  endpoint         TEXT NOT NULL,
  model            TEXT,
  status           INTEGER,
  error_type       TEXT,
  streamed         INTEGER NOT NULL DEFAULT 0,
  started_at       INTEGER NOT NULL,
  first_token_at   INTEGER,
  ended_at         INTEGER,
  latency_ms       INTEGER,
  ttft_ms          INTEGER,
  input_tokens     INTEGER,
  output_tokens    INTEGER,
  cache_read_tokens  INTEGER,
  cache_write_tokens INTEGER,
  stop_reason      TEXT,
  cost_usd         REAL,
  request_json     TEXT NOT NULL,
  response_json    TEXT,
  truncated        INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX IF NOT EXISTS idx_calls_run ON calls(run_id, seq);
CREATE INDEX IF NOT EXISTS idx_calls_started ON calls(started_at);

CREATE TABLE IF NOT EXISTS tool_events (
  id           TEXT PRIMARY KEY,
  run_id       TEXT NOT NULL,
  call_id      TEXT NOT NULL REFERENCES calls(id) ON DELETE CASCADE,
  kind         TEXT NOT NULL CHECK (kind IN ('tool_use','tool_result')),
  tool_name    TEXT,
  tool_use_id  TEXT,
  is_error     INTEGER NOT NULL DEFAULT 0,
  content_json TEXT
);
CREATE INDEX IF NOT EXISTS idx_tools_run ON tool_events(run_id);
CREATE INDEX IF NOT EXISTS idx_tools_use ON tool_events(tool_use_id);

Run aggregates (call_count, token sums, cost, error_count) are maintained incrementally in the per-call transaction — never recomputed with table scans on read paths.

§11 · Interface

Web UI

Vanilla ES-module JavaScript, no framework, no build step: ui/index.html, ui/app.js, ui/style.css, served statically. Target modern evergreen browsers only. Rendering via small DOM-builder helpers; all provider content is inserted with textContent, never innerHTML (prompts are untrusted input — a prompt containing HTML must render inert, §12.3).

11.1Product design tokens (the app, not this spec page)

The UI is a dark instrument panel — the one place the product should feel like avionics: near-black #14161A surface, panel #1C1F25, line #2A2E36, text #E8EAED/#9AA0A8, international orange #FF5A1F for LLM activity and primary accents, signal blue #5B8DEF for tool activity, green #3FB868 ok, red #E5484D errors. Type: system UI stack for labels; monospace stack for all numerals, ids, and payloads. Numbers use font-variant-numeric: tabular-nums.

11.3States & interactions

  • Empty DB: setup card with the two export lines from §05.1 and a copy button — the empty state is onboarding.
  • Live: SSE per §10.1, auto-reconnect with capped backoff (1→30 s) and an "offline — reconnecting" pill when down. Autoscroll follows new calls unless the user has scrolled up (resume via "jump to live" pill).
  • Keyboard: j/k next/previous call, enter open detail, esc close, g jump to live.
  • Header per run: name (click to rename → future; v1 read-only), total tokens, est. cost, duration, Export button (§10.6), Delete (confirm).
  • Accessibility floor: visible focus rings, semantic buttons/lists, color never the sole error signal (icon + text), prefers-reduced-motion disables the streaming pulse.
§12 · Trust

Security & privacy

12.1Network posture

  • Bind 127.0.0.1 by default. --host with any non-loopback value MUST print: "WARNING: orangebox has no authentication. Binding to <addr> exposes every recorded prompt to your network."
  • Outbound connections: only the two provider origins in §04, only in direct response to proxied client requests. The process makes no other network calls — no version checks, no telemetry, nothing (§02.2).

12.2Credential handling (MUST)

  • Persisted request headers are an allowlist — content-type, anthropic-version, user-agent — everything else is dropped before storage; additionally any header whose name matches /auth|key|token|secret|cookie/i is never stored even if allowlisted by mistake.
  • API keys exist in process memory only for the lifetime of the upstream request and never appear in logs, errors, the DB, exports, or the UI.
  • Body content is stored verbatim (that is the product), so README and UI footer both state plainly: the database contains your prompts; exports contain your prompts; treat both accordingly.

12.3UI safety

All recorded content rendered via textContent (§11). The UI ships zero third-party scripts, fonts, or CDN references — it must work fully offline.

§14 · Failure atlas

Edge cases & failure modes

14.1Error classification (error_type)

Conditionerror_typeClient seesRecorded
Upstream 4xx/5xx (incl. 429, overloaded)http_<status>Exact upstream status + bodyFull pair; retries by SDKs appear naturally as sibling calls — the timeline makes retry storms visible, which is a feature.

14.2Content edge cases

  • Huge payloads: any single stored JSON blob > 2 MB → truncate string leaves (longest first) to fit, set truncated=1, insert marker "…[orangebox: truncated N bytes]". Structure survives; bulk text is cut.
  • Base64 images / documents in messages: replace data with "[orangebox: base64 <kind>, N KB removed]" before storage — they bloat the DB and the UI can't meaningfully show them in v1.
  • Non-JSON bodies, malformed JSON, unknown endpoints under a provider prefix (e.g. /v1/models): proxy faithfully, store raw with null extractions, render as "unparsed call" in the UI. Never block traffic because we can't parse it.
  • Tool loops: multi-turn tool_use/tool_result chains are the normal case — §07.4 linking must handle N cycles per run, interleaved across calls.
  • Port in use: clear exit message. DB locked (second instance, same DB): exit with "another orangebox is already recording to this database — is one running?".
  • Clock: all times from Date.now() on one machine; monotonic enough for v1.

§17 · Verification

Acceptance criteria

17.1Checklist (all MUST pass before tagging v1.0.0)

  1. Fresh machine, two commands (npx orangebox; export + run agent) → first recorded call visible in UI in < 2 min.
  2. Byte-fidelity: for both providers, streamed and not, response through orangebox is byte-identical to direct (assert with a diff harness in tests using the mock upstream).
  3. A 3-call tool-loop run shows: 3 orange nodes in order, blue tool_use/tool_result chips between them correctly paired, sensible latencies, token counts matching the provider's usage fields, non-null est. cost.
  4. Grep the DB file for a known API key after a session → zero matches.
  5. Kill the agent mid-stream → call recorded as client_aborted with partial content; UI flags it; server stays healthy.
  6. Stop and restart orangebox → all history intact; deep link /run/:id still resolves.
  7. 429 from upstream (mock) → client receives 429 body unchanged; call recorded as http_429; timeline shows the retry sibling calls.
  8. 1000-call synthetic run: UI opens within budget (§13); server RSS within budget.
  9. orangebox export file re-imports mentally: contains everything needed to understand the run with no DB access.
  10. npm test green on Node 18, 20, 22 in CI. No network access in tests.

§21 · Reality check

Prior art & positioning

Added REV B, 2026-07-28, after competitive research. This section did not exist when the M0–M4 plan in §16 was written. It exists so the implementing AI does not build v1 blind — read this before M0.

Headline finding

The pain orangebox targets is real and already validated by the market — but the specific niche this spec describes (generic local SQLite proxy, both providers, env-var integration) is being squeezed from both sides by projects that are further along. Shipping the spec exactly as written in §01–§20 will land as a smaller, later clone of an existing tool. §21.3 gives the two changes that avoid that.

21.1The closest analog: claude-tap

A project called claude-tap is, mechanically, close to the same product as orangebox: a local proxy and trace viewer for AI agent traffic — system prompts, conversation history, tool schemas, tool calls, streaming responses, token usage — stored and viewed entirely locally, with common auth headers auto-redacted and a live SSE-driven viewer. It sits around 2.6–2.8k GitHub stars and has appeared on GitHub's trending page, so the format (local proxy → timeline UI) is proven to attract stars, not just plausible in theory.

The reason it's ahead is a sharper wedge than the one in §02: instead of asking the developer to set ANTHROPIC_BASE_URL/OPENAI_BASE_URL for their own agent code, it hooks directly into the CLI coding agents developers already run all day — Claude Code, Codex CLI, Gemini CLI, Cursor CLI, OpenCode, and others — with OAuth auto-detection so some setups need zero configuration at all. It also ships request diffing between turns and a static-HTML export for sharing, both of which are v2 items in this spec (§19).

21.2The rest of the landscape

Figures below are approximate, self-reported star counts gathered mid-2026 for orientation only — verify current numbers before making a positioning decision, the same way §08 warns not to trust the shipped pricing table.

Read together: the "single-player, fully local, zero-account debugging tool" shape is validated (claude-tap proves it draws stars), and the "production team platform" shape is validated at much larger scale (Langfuse, PostHog, LiteLLM). What's not validated, because nobody occupies it, is a fully-local tool aimed at raw SDK and custom-agent-framework traffic rather than the fixed set of CLI tools claude-tap already covers.

Decision — how this changes the spec

Two changes, applied on top of §01–§20 rather than a rewrite:

1. Reposition, don't rename the wedge. Keep the §06 proxy architecture exactly as specified (it's the right mechanism), but position orangebox explicitly for people writing their own agent code with the Anthropic/OpenAI SDKs or a framework like LangGraph — "the recorder for the agent you're building," not "the recorder for the agent CLI you're using." The README (§18) should name this distinction plainly rather than let a reader assume overlap with claude-tap.

2. Pull one v2 item into v1 as the headline differentiator. Of the §19 roadmap, request diffing between two calls or two runs is the cheapest to build and the one competitors already treat as core — ship a basic version in M3 (§16) alongside the timeline, not after. Replay (§19.1) is the higher-leverage differentiator long-term but is correctly sequenced as v2; do not pull it forward, it's too large to fit the M0–M4 timeline without threatening the 2-minute install promise in §17.1.
